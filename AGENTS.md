**0.3.14 landed** the browse-parity batch (D6 + A-1…A-6). Rules that must survive future edits:

- **Tab ids** come from `TabRegistry` (monotonic, never reused). Never derive them from `context.pages()` index again — that renumbered tabs on close.
- **Refs** are unique per driver and stored **per tab**, in the driver *and* in `BrowserSessionState`. Do not reintroduce a single per-session ref set: switching back to a tab must not require a re-snapshot, and a ref from another tab must be rejected by name.
- **Guardrails** live next to the tools: read-only tabs (`TabScopeStore`), debug tools (`browserAgentDebugTools`), idle close (`browserAgentIdleClose`), and `diagnose()` for launch failures. Keep the "why + next step" wording; do not replace it with bare error codes. The read-only guard covers the replay paths too (`browser_demonstrate` with `replay: true`, `browser_demo_recipes` run): a recorded flow must never be the way around a tab the user marked read-only. **Mutating browser tools carry the control's name**: `browser_click` / `browser_type` require `label` whenever the snapshot knows a name, the host rejects a label that does not match that ref, and `browser_demo_recipes { action: "run" }` accepts the `site` from `list` and rejects a mismatch. This is not cosmetic: the official permission layer (including the experimental auto-review) sees only the tool name and arguments, so the arguments must say what will be clicked and on which site, or a reviewer cannot authorize the call. **Browser mutations honour the official permission state**: read both the preset (`permissionPresets.current`) and the approval policy (`approval.effectivePolicy`). `read-only` refuses whatever the policy says, `auto` never shows our card (the per-call reviewer is the gate), and policy `never` counts as full access so custom combinations and future presets are not double-asked. `workspace-write` with policy `ask`, or a host missing both services, keeps the local card — the browser sits outside the workspace, so the preset has no opinion there. Do not move the card onto `tools/pre-execute`: the official `ask` has no site-session grant and no control preview, so a multi-step repair would become one card per click. **Unattended runs are granted per flow, not per session**: when the user marks a saved flow 无人值守, running it adds one bounded origin grant (`BrowserApprovalGate.grantOrigin`: same origin as the recording, the budget from Settings — default 20 minutes / 30 actions, clamped to 5–60 minutes / 10–200 actions) that covers the replay and the repairs it needs; it is never persisted, never covers another site, and expires on time or budget; a refused or aborted run revokes it immediately (`revokeOrigin`) so a denied run cannot leave the site open. Secrets still stop. Do not derive it from the session's permission mode or from "looks like a scheduled task". **A run leaves a trace**: every run records `lastRun` (time, `ok`/`stopped`/`failed`, counts, a capped reason) on the flow, never page content; an unattended run without a visible outcome is a black box. Recording it must not bump `rev`. **The dedicated browser clears `navigator.webdriver`** through the `hideWebdriver` init script (Chromium and WebKit), because login gates (Bilibili and friends) reject the environment even with correct credentials. Do not do it with `--disable-blink-features`: Chrome paints an "unsupported command-line flag" warning bar for it, and the bar costs more trust than the flag buys. `tests/browser-agent-webdriver.test.ts` pins both (script clears the value, args stay clean). Do not extend this into a stealth toolkit (patched plugins, canvas noise) — it breaks on the next Chrome and is not our fight.
- **Debug capture never records headers, cookies or response bodies**, and console text goes through `redactText` (Chrome writes request URLs into `Failed to load resource` messages).
- **`playwright-core` stays lazily imported**; `lazy-playwright.test.ts` fails if a runtime static import comes back.
- **Demonstration recording** (`browser_demonstrate`) streams user steps to the host through `context.exposeBinding('__dshDemoPush')` — page-side buffering loses everything when the user submits a form and the document navigates. Secret fields are masked on both sides. Recording arms **every tab** of the dedicated browser (plus new ones) and tags each step with `tabId`/`tabUrl`; never narrow it back to the bound page — users carry flows into tabs they opened earlier. The on-page recording badge is styled through CSSOM (a `<style>` element dies under a strict `style-src`), stays `pointer-events:none` + `aria-hidden`, and lives in a shadow root. Replay (`demo-replay.ts`) matches steps to controls by **role + normalized name** against a fresh snapshot and stops at the first step it cannot reproduce honestly — a masked secret, a `<select>`, a missing control. Never let replay report a flow as finished after it stopped; the returned `pending` steps exist so the model can continue. Saved flows outlive the browser run that recorded them, so **never trust `tabId` inside a stored recipe**: replay only switches tabs for multi-tab flows, re-maps ids by page URL, and reopens the recorded `tabUrl` when that tab is gone. Saved flows are agent-callable through `browser_demo_recipes` (list / run by name); a run needs one approval card and reuses the same replay, so `<select>` and checkboxes replay while masked secrets still stop. **Flow parameters** are `${name}` tokens inside a fill value or a navigate URL, with the pre-parameterisation literal kept as the recipe's default, so an untouched flow still runs exactly as recorded; masked fields cannot be parameterised, and a run missing a value stops with the variable names instead of typing the raw token. **Variables are named the way the page names them**: `label` is what the user sees (「开始日期」, may be Chinese) and is derived from the recorded control, while `name` stays a generated token id (`v1`) that only appears inside `${…}`; `vars` keys match either, and `resolveDatePhrase` turns 今天 / 上周 / 上季度 into a local ISO date before the model is ever asked to do date arithmetic. A variable also carries `ask`: the recorded `default` stays (it is what "改回固定" restores) but every run must supply it, and `removeVariable` writes the literal back into the steps rather than leaving a dangling `${…}`. **Repairs** (`demo-heal.ts`) are the only way a saved flow learns after a site change, and they only ever rewrite a control's **locator**: the recorded value, the order and the step count change only by the steps the agent visibly added before the control. A masked secret is never a drift and is never stored, the tracker observes `browser_click` / `browser_type` / `browser_navigate` only while a flow is stopped (same tab, ten-minute window), and `commit()` writes a *proposal*; `resolveHeal({ accept: true })` is the only path that rewrites steps and it keeps a bounded version history so the panel can undo it. Never auto-apply a repair, in any session, for any reason: an unreviewed write changes what the next run does, and the unattended case is covered by the per-flow origin grant above, not by silent learning. Never let a stale `tabId` or `ref` into a repair.

Same fragment→Session mapping as official `@deepseek-ai/dsh-deepseek-chat-import` (THINK→reasoning, `web_search` / `web_fetch`) when the API payload includes those fragments. Do **not** silent-fallback current chat to DOM when the session API fails — fail and suggest share. **Remote control (`remoteControl`)** is user-facing, **on by default**, and ships **WeChat + Telegram + Feishu**. Being on is inert: nothing is intercepted until a chat is paired and a channel is running. Rules that must survive edits:

- **An approval is offered on both surfaces, never captured by one.** `shouldHold()` only decides whether to offer a remote card; the waterline hooks must still call `next()` so the official desktop approval / question card appears too, then return the first decision that arrives. When the desktop wins, drop the remote pending with `dropPending(code)`; when the chat wins, return the **official outcome vocabulary** (`allowed-once` / `rejected`), not `approve` / `reject` — the approval service normalizes unknown values to `unavailable`, which fails the tool and leaves the desktop card looking unanswered. **Every** decision, from the desktop or from any paired chat, fires `onDecision` and pushes a `decided` notice to **all** paired chats with the deciding `chatId`; the hub labels the source (桌面 / 微信 / Telegram / 飞书). A second tap on an already-decided ask must get "no pending", never a second decision. An earlier build returned `handle.wait` without calling `next()`, so sitting at the desktop showed no approval and the only way out was logging out of remote control. `tests/remote-host-bridge.test.ts` pins both winners. A session the host has not indexed yet must be refreshed once before deciding to fall through — a brand-new session's first approval otherwise reached only the desktop and looked like "WeChat stopped receiving approvals". Never let a non-decision settle the race: the official answerer can immediately return `unavailable` / `cancelled` (or an empty answer) when no card was shown, which otherwise kills the remote card the instant it is pushed.
- **A closed channel releases its asks.** When the last channel stops or logs out, the hub calls `controller.releasePending()` (approval → `reject`, question → empty answer). A tool must never hang on a channel that no longer exists; do not delete that call.
- **Pairing is one-shot and channel-scoped.** Codes are 6 digits, in memory only, 10 minutes, never written to disk; a WeChat code sent to the Telegram bot is refused without burning the code. Bindings persist, each channel's token lives in the host credential service (no plaintext fallback). The bindings file must round-trip **every** `RemoteChannel`: `BindingStore.load()` once accepted only `weixin`, so a restart silently un-paired every Telegram chat while the card still said "connected". `tests/remote-bindings.test.ts` pins the Telegram reload.
- **No token reaches the client.** `remoteStatus` carries channel phase / login / devices / handle only; each channel's token stays inside that channel and the host credential service.
- **The frame-wide status pill is a shortcut, not a second switch.** `RemoteStatusPill` lives in `shell.overlay` (the official click-through frame layer), shows the same `remoteControlEnabled` config and the live `remoteStatus` channel count, and toggles that one config path via `persistEnhancerSettings`. It never introduces a second "listening" state; stopping messages must stop the same hub the Settings switch stops.
- **Proactive push is not guaranteed on every channel.** WeChat iLink rejects sends with `ret=-2` once the inbound `context_token` goes stale (the user must message the bot again); Telegram can be unreachable from some networks. `pushNotice` catches these, calls `channel.reportSendError()` so the channel card shows a real reason instead of "connected", and never claims delivery. Feishu's long connection is the reliable channel for approval pushes. A WeChat send rejected with `-2`, or more than two hours without any WeChat inbound, triggers a throttled desktop OS notification (`remote-wechat-stale`, at most once per 12h) telling the user to message the bot before walking away; the warning clears on the next inbound message or a successful send. `remote/debug-notices.enabled` (plugin-data) opts into metadata-only routing logs, never message content.
- **Each channel owns its transport and cursor.** WeChat keeps its QR login and per-message `contextToken`; Telegram uses a Bot Token + long polling (no webhook, private chats only, 401/403 fatal, offset persisted in `telegram-cursor.json`); Feishu uses App ID + App Secret and a **WebSocket long connection** (no public URL, bot DMs only). Feishu is push, so its transport queues events and `getUpdates` drains them; `card.action.trigger` answers inside the socket response (a toast) while the command itself still goes through the poller. **Feishu setup is guided in the card, template first** (the console's 「创建飞书智能体应用」 presets the bot, scopes, events and card callback), with the 5-step manual path folded behind a toggle (per-app deep links to permissions / event config / callback config / app, and a copyable scope list). The card must keep saying that `card.action.trigger` lives under **回调配置**, not the event list, and that the manual scopes are `im:message.p2p_msg:readonly` + `im:message:send_as_bot` (+ `im:message.readonly` for card callbacks). The Feishu SDK is a ~30 MB runtime dependency: keep it **external and dynamically imported** (`tests/remote-feishu-lazy.test.ts` fails on a static import), because loading it at plugin start would tax every user who never connects Feishu. Telegram advertises `buttons: true`: command replies and pushed cards carry inline keyboards, `callback_data` is the same command a user would type, and every callback query is acknowledged after handling. The task list gets picker buttons for active/recent tasks (capped); the full list stays text. Adding a platform means a transport + a channel wrapper over the shared poller, never a second task board; `REMOTE_CHANNELS` in `bindings.ts` is the single list every hub/status/RPC/UI path must cover.
- **The QR encodes `qrcode_img_content` itself.** Opening the liteapp page and scanning the page's own QR fails with「网络错误」. `src/client/remote/qr.ts` is a small byte-mode encoder verified against jsQR (L/M/Q/H, versions 1–20, UTF-8); do not swap it for a "open the link" shortcut.
- **Pending approvals are not persisted.** A host restart has no waiter to answer them, so old cards are history, not buttons.

- **Sessions are driven through `ctx.sessionController`.** Fold `list` / `prompt` / `cancel` over that host service; this Desktop build does **not** provide the older `apiProxy` seam, and assuming it did left the task list empty. A failed bridge is retried (bounded, once per 5s up to 12 tries) because the service can register after plugin apply.
- **One board.** The runtime must adopt `bridge.controller`; a second `RemoteController` receives no host events and silently answers「当前没有任务」. The session list also warms up late, so the adapter re-reads it before every command and the bridge re-reads it when an unseen session emits an event.
- **Control words tolerate how people type.** `切1`, `切换1`, `选1`, `详情4`, `批准a3f9` and a bare `1` after a list are commands; a sentence that merely starts with one (`继续优化这段`, `暂停吧`) stays a message. Approvals are never inferred from casual words.
- **Push the result, not only the request.** Approval and question cards (with their code), turn failures, and the model's final answer on **every completed turn** of a tracked task — whether it started on the desktop or from a chat. A remote user must be able to read the answer and continue. Card actions must name their task explicitly (`详情 N`) and never rely on the chat focus. `详情` shows the live answer, and when there is none (a turn that ended before the channel or the host started) it reads the last assistant text back from the session history through `readAnswer`; never answer a `详情` with status alone when the session has text. Pushes go to paired chats only, use the last inbound `contextToken` when the platform needs one, and never contain the bot token.
- **Focus sticks to the chat.** `切` stores the chosen `sessionId` on the binding row; a restart restores it only if the task still exists, and the session cleaner clears it when the session is deleted. With no explicit focus, exactly one waiting task is chosen automatically. Another task's notification never steals an explicit focus, but `详情` (bare or numbered) selects the task it shows, and bare `详情` prefers a lone pending task so an approval cannot be hidden by an older focus. **A focused card is a view of one task, not a picker**: `切 N` and `详情` render that task's card (status, pending, latest answer) with only its own actions (暂停/继续/批准/拒绝/详情). The task-list buttons belong to the `任务` command alone; never append the picker to a focused card — that turned switching into an endless list loop.

## Browser agent — platform rules

| OS | Settings / sidebar choices | Auto order |
| --- | --- | --- |
| **macOS** | `auto` · `chrome` · `safari` (no Edge) | WebKit → Chrome |
| **Windows** | `auto` · `chrome` · `edge` | Edge → Chrome |
| **Linux** | `auto` · `chrome` | Chrome |

- Safari option launches Playwright **WebKit** (Safari engine), **not** branded `Safari.app`. Require `/Applications/Safari.app` as a platform gate; require `npx playwright install webkit` for the engine binary.
- Cross-OS coerce: saved `edge` on Mac → `safari`; saved `safari` on Windows → `edge`.
- Auto isolates profiles per channel (`profile-auto-webkit`, `profile-auto-chrome`, …). Never share one user-data-dir across Chromium and WebKit.
- **Sticky Auto:** once Auto successfully falls back (e.g. to Chrome), keep that channel for the running driver. Do **not** tear down every Agent tool tick just because WebKit is listed first — that caused open/close flaps.
- Mac Chrome/Safari candidates check both `/Applications` and `~/Applications`.

## Soft pause covers the lineage

The soft-pause gate keys on a Session id, and a subagent runs as its own Session (`header.parentSession`). A parent-only check therefore let a paused session keep spending: the child stepped and requested while the parent sat parked. `agent/pre-step` now walks `sessionLineage()` — own id, then ancestors while `header.origin === 'subagent'` — and holds while **any** of them is engaged. A fork keeps `parentSession` but is an independent conversation, so it is not covered; that is the same rule the official archived-session gate applies. Aborting the child drops nothing: `clearOnAbort` names a single session, so a stopped subagent cannot resume its parent. `tests/soft-pause-lineage.test.ts` pins hold, multi-level, fork, reverse, abort and "wait for every engaged ancestor".

The **control** must watch the tree, not the turn: a parent hands off in seconds, so visibility is `running || engaged || treeRunning`, computed by `isTreeRunning()` from the live `agents.list()` (status `running` + lineage). A parent-only `running` flag hid the one button that could stop the child, which is the case a pause is actually for. `tests/soft-pause-tree.test.ts` pins child, two-level, unrelated-tree, fork and running-root cases.

## UI must imitate official DSH source

When adding or restyling client UI that peers an official Desktop surface, read the matching `@deepseek-ai/dsh-client-ui-*` package (`lib/client.js` + CSS) and reuse primitives (`FileTypeIcon`, guide artwork, folder icons, tokens). Do not invent parallel chrome. See `.cursor/rules/dsh-ui-style.mdc`.

**Only reference design tokens the theme defines.** A `var(--dsw-…)` with an unknown name is dropped, so the declaration silently never applies: that is how the browser approval banner lost its background and rendered see-through over the page (`--dsw-alias-bg-elevated` was never a token). `tests/client-design-tokens.test.ts` fails if `styles.module.css` mentions a token missing from `tests/fixtures/dsh-theme-tokens.txt`; refresh that fixture from `@deepseek-ai/dsh-client-ui-theme` when the Desktop host moves.

## Backlog admission: prove the official surface does not do it

Before planning or implementing a roadmap item, write its three-line duplicate check: the official package/UI surface that would own it, the evidence (screenshot, code path, or test), and what stays uncovered. If the third line is empty, delete the item from the roadmap instead of building it — a plan for a duplicate feature is the most expensive kind of plan. Check by **surface**, not by feature name: L1 (run progress) was justified with "official Todos only cover the plan", missed the conversation's activity block, and had to be reverted after shipping.

Plans live in `docs/plans/<name>.md` (local-only); the check is the first section.

## No orphan features — every capability needs a settings toggle

User-facing capabilities **must** appear under **设置 → 智能体增强 → 功能** with an on/off switch in the **same change set** (`MODULES` + Config + `SETTINGS_FEATURE_GROUPS` + locales + runtime gate). Do not ship always-on surfaces with no switch. See `.cursor/rules/no-orphan-features.mdc`.

The Features page shows a switch and one-line description per capability. Small controls (alert level, model entry, remote manage) stay inline; only a genuinely large option set (browser agent) sits behind a clearly styled **高级设置** Button, closed by default. Channel setup for remote control lives on the **远程连接** tab while its master switch stays in Features: Features enables, Remote connects.

## Persisted data must not hold volatile handles

Anything saved and re-run later (demo recipes, bookmarks, caches) must store semantics, not runtime handles: no `tabId`, no element `ref`, no page/window/process object, no temp path, no per-run counter. Re-resolve from the URL / role+name / current DOM at run time. When the target is gone, stop at the exact step with a reason; do not poke at a stale handle.

This is not theoretical: saved demo recipes originally kept the recording's `tabId`, so after a restart replay died on step 1 with "tab 1 is no longer open". Recipes now drop `tabId` on save, keep `tabUrl`, and match live tabs by page URL. The planning template (`docs/plans/_template.md`, §4) carries the same checklist.

## Session delete must stay thorough

When a session is deleted from this plugin, **all plugin-owned persistence for that `sessionId` must be purged**.

Any new feature that writes per-session data under `plugin-data` (or elsewhere keyed by session) **must** register a `SessionCleaner` in the same change set and update `docs/architecture/session-delete.md`. Leaving orphan session files after delete is a product bug.

See: `docs/architecture/session-delete.md` (local-only).

## Publishing needs an explicit ask

Shipping is a separate decision from building. **Never run `pnpm publish`, push a `v*` tag, or create a GitHub release unless the user asked for a release in that turn.** Finish the change, run `pnpm check`, and report the version you *would* publish (plus what changed); wait for a go-ahead. Batch related work into one release unless the user asks for separate ones — ten patch releases in two days is a process failure, not shipping speed, and published versions cannot be taken back cleanly.

## Docs policy

Publish only what stays true: `README` (what the plugin does and does not do), `CHANGELOG` (what shipped), `AGENTS.md` (invariants), tests. Keep plans and decision logs local under `docs/` (ignored by git) — an AI-written roadmap in a public repo reads as a promise and rots fastest. Do not add `docs/roadmap.md` or `docs/architecture/` to git without an explicit decision to publish them.

## CI

`.github/workflows/ci.yml` runs on push to `main` and on PRs: `pnpm check` (typecheck + vitest + build + pack verification) on Ubuntu, plus typecheck/tests on Windows. The integration suite under `tests/` ships with the repo (sanitized: no real home paths, tokens or chat content — keep it that way); `vitest.global-setup.ts` (tracked) builds `lib/` once when it is missing.

## Host version policy

We stay on `0.x` while the host is pre-stable. The plugin is an extension of DeepSeek Desktop, so it must not claim more stability than the platform it extends: no `1.0.0` until the Desktop host leaves pre-release. A milestone version (`0.4.0`) is still the right way to close a batch and put the patch noise behind one number.

Desktop ships its own `@deepseek-ai/*` packages, so the plugin has two version lines: `devDependencies` pin the newest candidate we build and test against (currently `0.2.2-rc.5`), while `peerDependencies` accept `>=0.2.2-rc.2 <0.3.0-0` so a Desktop that has not taken the latest candidate still loads the plugin. `tests/package.test.ts` enforces that shape (peer mirrors dev exactly, or the range; dev is always a concrete version). When a new candidate lands, check its real source diff — the GitHub compare API caps at 300 files, so pull both tag tarballs and hash-compare the trees instead — then bump devDeps only.
